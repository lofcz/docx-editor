# Sciobot DOCX adapter

Private application adapters over the native DOCX engine. The canonical package owns document state.

The runtime uses one external core peer, the Apache Markdown converter, `diff`, and the application's remark pipeline. The build checks its module graph for copied native code and excluded runtimes.

Run checks from the repository root:

```bash
bun run --filter '@sciobot/docx' typecheck
bun run --filter '@sciobot/docx' test
bun run --filter '@sciobot/docx' build
```

The package test command loads the repository DOM environment explicitly. It works from the package working directory.

## Reference fixtures

These commands execute the application reference and capture its behavior:

```bash
bun scripts/sciobot-port/capture-ai-reference.mjs
bun scripts/sciobot-port/capture-matcher-reference.mjs
bun scripts/sciobot-port/capture-tool-reference.mjs
bun scripts/sciobot-port/capture-mdx-reference.mjs
```

Each command accepts the application checkout as its first argument. AI capture accepts the Plate checkout as its second argument.

Fixtures include source revisions and content hashes. Tests read committed fixture data without executing Plate.

Tool capture executes the original schema factory, read/search helpers, and executor closure. It uses an identity SDK wrapper and immediate review delegate. Mounted hook routing and streaming have separate backlog leaves.

## Native data and writes

Call `prepareNativeDocument(bytes)` before opening imported bytes in the native workspace and before creating a collaboration room. The application prepares raw imports in `prepareWorkspaceDocument`; the room creator prepares the initial shared bytes before any peer joins. Pass live room handles through unchanged. Do not initialize each peer independently after joining a room.

Preparation creates an empty application payload store before room bootstrap. Concurrent first block writers then share its lifetime, and either actor can undo without orphaning metadata. Preparation creates the application code character style and its imported-character-style variants as initial document content. It also creates an empty numbering root when the document has no numbering infrastructure. This root and its namespace belong to the initial document, so undoing the first list cannot remove them. Imported numbering parts and relationships stay intact. Shared application list fragments refuse if the required numbering infrastructure is missing. It has no undo entry. Each actor's later code formatting remains independently undoable, including when the imported DOCX had no styles part. Derived definitions also stay outside actor history, so undoing another actor cannot remove a definition used by surviving code spans. Preparation preserves original body, furniture, media, pending revisions, and recovery metadata bytes; it serializes only changed payload infrastructure, styles, numbering, relationships, and content types. It does not run Word export cleanup. Repeated preparation returns the same bytes.
